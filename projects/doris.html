0. Context and architecture

The company's analytics and serving layer for fraud events ran on ClickHouse. I led the move to Apache Doris in compute-storage separation mode, self-managed on AWS and Kubernetes. The platform is in production now. A lot of the numbers on this page were measured earlier, on a production-scale preprod cluster or on smaller trial clusters, and each one is labeled with where it came from.

What makes this layout worth the trouble: table data lives in S3, so a compute group is a metadata construct. Scaling the heavy group from 2 to 4 backends moved no data; tablet ownership was rebalanced as a metadata operation. That is the property everything below leans on.

1. Engine selection and rebuild

Problem. Fraud serving traffic and analytics queries shared one ClickHouse instance. I measured seven days of its query log: 13.9M queries, of which 5.2M were real business queries after dropping the system self-queries (55% of the total, mostly heartbeats). Query rate had p50 8, p99 48 and a max of 251 per second. The 10% of queries that scan more than 1M rows consumed 95.7% of all rows read. Three configuration facts mattered: max_concurrent_queries was 1,500 against a real concurrency mean of 2.4 (a limit that never fires), the per-query memory cap was 20 GiB, and the server-wide budget was 432 GiB, so about 22 heavy queries could exhaust it. There was no layer in between that gave a workload class its own budget. On top of that came a schema change roughly every 6 minutes (1,678 ALTERs in 7 days) on tables about 3,700 columns wide.

What I did. I ran the selection as constraint elimination, not as a speed contest. The hard constraints were open source and deployable on our own AWS and Kubernetes. Our own benchmark showed ClickHouse still faster on the workload we cared about, and the case was argued with that on the table. The argument that carried it was the missing isolation layer above, not a latency claim. Then I led the rebuild: schema migration design, the pool layout, and the engine work in the sections below.

Evidence. The log numbers are from the ClickHouse instance, measured on 2026-09-14 to 09-20. Two full write-ups exist: the decision (w-g-why-doris, "Choosing Doris Without a Speed Win") and the migration case study (w-cs-doris, "Rebuilding the fraud event store, down to the engine").

2. Query cost estimation and routing in the Doris FE; elastic scaling and cache warmup

Problem. After consolidation, fewer than 1% of queries were heavy, but one misplaced heavy query could starve the shared light pool. Scaling a compute pool takes minutes; a memory blow-up takes seconds. So the heavy/light decision has to be made at plan time, before any backend touches data. Stock EXPLAIN was not good enough for this: on my 52-query suite it routed correctly 45% of the time and missed 27% of the heavy queries. Identical query templates with different parameters produced byte-identical EXPLAIN text while memory differed 23x.

What I did, routing. This is engine-level work on a Doris fork, proposed upstream (not merged). I added two SQL statements to the FE. EXPLAIN ESTIMATE PLAN exposes the per-operator estimates the optimizer already computes and then throws away, as structured JSON. EXPLAIN ROUTE PLAN adds a classifier on top: 10 structural rules and one pessimistic fallback, returning a verdict in 6-8 ms regardless of data volume (13M and 102M rows both plan in about 8 ms, because it only reads cached statistics). The branch diff against Doris 4.0.5 is 13 files and +1,994 lines for the two statements; the first statement alone is 7 files and +749. Thresholds are hot-reloadable config, so changing one is a SQL statement rather than a 44-minute image build.

Two things I got wrong and fixed. One query reading 5.06 billion rows was labeled light because the estimator multiplied selectivities across join legs and under-counted by about 580x; the light pool's limit killed it in 3 seconds. And a wide SELECT * over 3,727 columns took 253 s cold while the byte model called it cheap. After the live audit I removed the whole class of rules that depended on byte estimates (19 reason points down to 11) in favor of structural signals such as operator shape and output column count. I also decided the classifier policy would not go upstream, only the estimate mechanism, because the policy is full of company-specific thresholds.

What I did, elastic tier. The heavy group rests at zero replicas. I built the control plane for it (dcluster Doris write path, then the separate doris-autoscaler): one write primitive that patches a single replicas field, idempotent scale semantics, and a queue-driven loop that scales on waiting > 0. I had designed a multi-signal version with CPU and slot percentage; load testing showed CPU gave false positives and false negatives and the slot signal was unreachable under FE admission, so I deleted it. Capacity is discrete, not per-query: node boot is about 66 s and backend registration about 2 minutes, while heavy queries run 60-500 s, so per-query elasticity would mostly arrive late. Readiness is layered and assumes every signal lies: a pod count is not trusted, SHOW BACKENDS must show the group alive, then a canary query must touch storage (a SELECT 1 is folded by the FE and never reaches a backend).

Cache warmup, stated precisely. The file cache sits on persistent volumes, so a restarted backend reloads its cache instead of starting empty. Warm-up runs as Doris warm-up jobs in their own workload group, which also keeps them out of the cost accounting in section 5. What is not done: activating a new group member does not wait for warm-up to finish, so a new member serves with a cold cache for a while.

Evidence. Heavy-query recall 15/15 on the canonical suite (production-scale preprod). Light-query precision 45/50 = 90%, on 50 real queries sampled from a production query log but run on a table shrunk 500x, early classifier version. On the live FE, 14 of 14 declared query shapes agreed. The 197-case Java/Python corpus is a parity check between the two implementations, not an accuracy figure. Total cost: down about 29%. That is an estimate; it has not been reconciled against an invoice. Deep articles: w-p-routing (engine-level routing), w-p-elastic (elastic compute tier), w-p-fanout (point-query fan-out, the third engine change).

3. Production migration

Problem. The event table is about 3,700 columns wide and sits on billions of rows per region. Migrating it hit limits that do not appear on narrow tables.

What I did. I designed the ClickHouse-to-Doris migration for the production regions: about 100 billion rows and up to 4,000 columns in total. The pipeline exports from a ClickHouse snapshot to S3 and loads into Doris native tables. Four memory breakpoints needed separate fixes: the Parquet footer (row groups x columns, 2.12 GB for one file), scanner memory that exec_mem_limit does not govern (about 78 GB per backend), the export buffer tradeoff, and load memory that grows with the target table. At about 1.7B rows a load livelocked: 40 GiB baseline plus 25 GiB per load, so two concurrent loads broke a 90 GiB ceiling; capping concurrency at 1 fixed it. Compaction fell over twice, and I kept the two incidents separate: auto-compaction disabled at table creation (compaction score about 2,500, about 2,500 segments per tablet), and orphaned tablets from a dropped table (score about 4,504). The fix for the first (auto-compaction on, 2 GiB write buffer, monthly dynamic buckets) took a tablet from about 2,500 segments to about 10.

Evidence. Validation was done on a production-scale copy of the largest event table in preprod, reconciled at 99.945% by row count. The 0.055% difference is attributed to duplicate source rows merged by dedup semantics; the attribution is by mechanism, I did not keep a per-row table. The compaction fix was verified on a slice of about 6% of the data, not the full table. Deep article: w-cs-doris.

4. Capacity and disaster recovery

Problem. An earlier sizing plan used 15 TB. That was an EBS volume size, not a data size. Separately, nobody had run a restore.

What I did, capacity. I redid the plan from measured source volume: three wide tables, 6.4 TiB. Replacing volume size with data size removed about 2.5x of over-provisioning. Pool depth I took from 90 days of hourly peak concurrency, after removing 35 pile-up hours where a backlog had inflated the number: p50 9, p90 23, p99 60.8, max 138. I used p99 as the anchor for a provisioned floor and left the tail to elastic capacity. The model covers one production region; several inputs are marked as inferred.

What I did, DR. In compute-storage separation the thing to protect is metadata, since the data is in S3. I built a toolchain: metadata bundles to S3 every 12 hours, a five-phase in-place restore with all destructive steps isolated in one CLI, cross-cluster copy through an API, and precheck, teardown and guard commands. I evaluated a point-in-time layer for the metadata key-value store and dropped it in late September. S3 versioning is off.

Evidence. All measured before production. In-place restore of 2.74 TB / 1,799 tablets in preprod: 55 minutes clear-to-promote, with about 25 minutes lost to one failed attempt and retry. Full end-to-end DR run on a dev cluster: about 22 minutes. Fault injection, 17 scenarios on the dev cluster, 15 verified with zero data loss. The most useful output of the drill was 8 gaps in the runbook and 1 tooling bug. I do not publish an RTO: one non-production run at one scale does not support a commitment. Deep article: w-p-doris-dr.

5. Tenant-level cost attribution from audit logs

Problem. Customers pay a fixed package fee, so nobody could say which tenants used how much, or how much of the platform's cost was capacity sitting idle.

What I did. I built it inside Doris with SQL and scheduled Doris JOBs, reading __internal_schema.audit_log. A snapshot of live backends every 5 minutes gives each compute group an hourly price. A query's cost is its slot time times the slot price of its own workload group; S3 reads are charged from the bytes it pulled from remote storage; S3 storage is charged per tenant database per day. Warm-up, compaction, cache hits and failed queries are not billed (failed ones are recorded as loss). Idle capacity is what remains: group cost minus billed, minus operator accounts, minus failed loss. Because the audit log only keeps 30 days, the hourly ingest copies it into a fact table.

Evidence. Preprod, 35 days, 422,150 queries. Query cost summed to the tenant totals and the compute-group reconciliation with a difference of 0. About 81% of normal queries cost under $0.00001. Of roughly $40 a day in preprod, per-query compute plus S3 reads was about 0.1%, S3 storage 18%, and the rest was idle capacity and fixed platform cost; compute-group utilization was 0.5%. That traffic is mostly load tests and operator accounts, so I use it to check the algorithm, not as a statement about production tenants. Not built: allocating FE and other shared components by tenant quota (preprod has no per-tenant quotas).

6. Observability

Problem. The platform started with no dashboards and no alerts, and most of its failures are silent. Three early incidents set the brief: a warm-up job pointed at a deleted compute group and failed for 35 hours; platform CI overwrote the compute platform's state 5 times before anyone linked the repeats; and the metadata store's single health signal sat frozen for 16 days while showing green.

What I did. A dashboard set of 13 sections and 95 panels, organized as two-tier triage. The first tier is a one-minute read for someone who has just been paged and has no context: it is ordered by layer, so the first screen already says which layer is wrong. The second tier is split into the same layers, so a drill-down lands in a named section rather than a search through dozens of graphs. The autoscaler gets its own view, because when it breaks the other panels can stay green while capacity stops following demand. For alerts I wrote 27 candidates, checked every expression against real metrics, and kept 12. The filter was one sentence: keep a rule only if it catches a silent or irreversible failure. Each blindness-prone rule has a pair that watches for the metric disappearing, since an alert on a vanished series never fires.

Evidence. The expressions were checked against real data; firing behavior was not tested end to end (no mutation tests). They are SLI/SLO-style health signals for silent failure, not latency burn-rate alerts, and a latency SLO layer is still to build. Deep article: w-p-doris-obs.

Boundaries

  • Work I did not do and do not claim: Arrow Flight result transport and the FE memory-kill backstop (partner team; I defined the output contract only); the Spark and Flink job-path reliability work in the same control-plane repo (spot interruption fallback, capacity admission, job audit, multi-cluster lock).
  • Spot instances for the heavy pool are a design. What runs live is on-demand.
  • The routing work is a fork. Nothing from it is merged upstream.

0. 背景与架构

公司的反欺诈事件分析与在线服务层原先跑在 ClickHouse 上。我主导把它迁到 Apache Doris 存算分离架构，自建在 AWS 和 Kubernetes 上。平台现在已经在生产运行。这一页里不少数字是更早在生产规模的 preprod 集群或较小的试用集群上测的，每个数字都会标出它在哪测的。

这个布局值得折腾的原因：表数据在 S3 上，计算组只是一个元数据概念。把 heavy 组从 2 个 backend 扩到 4 个，没有搬一份数据，tablet 归属是作为元数据操作重新分配的。后面所有设计都靠这一点。

1. 引擎选型与重建

问题。 反欺诈在线服务和分析查询共用一个 ClickHouse 实例。我分析了它 7 天的 query log：1,391 万条查询，剔除系统自查询（占 55%，主要是心跳）后是 521 万条业务查询。QPS 的 p50 是 8，p99 是 48，最高 251。扫描超过 100 万行的那 10% 查询，吃掉了 95.7% 的读行数。三个配置事实最关键：max_concurrent_queries 是 1,500，而真实并发均值是 2.4，这个上限永远不会触发；单查询内存上限 20 GiB，全局预算 432 GiB，所以大约 22 条重查询就能吃光；中间没有一层能给某类负载单独划预算。再加上约 3,700 列的宽表平均每 6 分钟一次 schema 变更（7 天 1,678 次 ALTER）。

我做了什么。 我把选型做成约束排除，而不是速度比赛。硬约束是开源、能部署在自己的 AWS 和 Kubernetes 上。我们自己的 benchmark 显示，在最关心的负载上 ClickHouse 仍然更快，论证是在这个事实摆在桌面上的前提下做的。扛住论证的是上面那个缺失的隔离层，不是延迟。之后我主导了重建：schema 迁移设计、池的布局，以及下面几节的引擎工作。

证据。 日志数字来自这个 ClickHouse 实例，测量区间 2026-09-14 至 09-20。有两篇完整的文章：决策篇（w-g-why-doris，选 Doris 那次 benchmark 明明更差）和迁移案例（w-cs-doris，重建反欺诈事件存储，一路改到引擎）。

2. 查询代价评估与路由（Doris FE 源码）；弹性扩缩与缓存预热

问题。 合并之后，重查询不到 1%，但一条放错池子的重查询就能把共享的 light 池拖垮。扩一个计算池要几分钟，内存爆掉只要几秒。所以 heavy/light 必须在计划阶段、任何 backend 碰数据之前判定。原生 EXPLAIN 不够用：在我的 52 条查询套件上只路由对了 45%，漏判了 27% 的重查询。同一个查询模板换参数，EXPLAIN 文本逐字节相同，内存却差 23 倍。

我做了什么：路由。 这是在 Doris fork 上做的引擎层工作，已向上游提议（未合并）。我在 FE 里加了两条 SQL 语句。EXPLAIN ESTIMATE PLAN 把优化器本来就算出来、然后又丢掉的各算子估计值，以结构化 JSON 暴露出来。EXPLAIN ROUTE PLAN 在这之上加一个分类器：10 条结构规则加 1 条悲观兜底，6-8 ms 给出判定，和数据量无关（1,300 万行和 1.02 亿行都在约 8 ms 内出结果，因为只读缓存的统计信息）。两条语句相对 Doris 4.0.5 分支的 diff 是 13 个文件、+1,994 行；单看第一条是 7 个文件、+749 行。阈值是可热加载的配置，改一个值是一条 SQL，不再是 44 分钟的镜像构建。

有两处我判断错了、后来改掉。一条读 50.6 亿行的查询被判成 light，因为估算器跨 join 腿把选择率相乘，低估了约 580 倍，结果被 light 池的限制 3 秒内杀掉。另一处是 3,727 列的 SELECT * 冷读 253 秒，字节模型却说它便宜。在线上审计之后，我把依赖字节估计的整类规则删掉（判定点从 19 个降到 11 个），换成算子形态、输出列数这类结构性信号。我还决定分类器的策略部分不进上游，只放估算机制，因为策略里全是公司特有的阈值。

我做了什么：弹性层。 heavy 组平时副本数为 0。我做了它的控制面（dcluster 里的 Doris 写路径，后来拆成独立的 doris-autoscaler）：只有一个写原语，只 patch 一个 replicas 字段；扩缩语义幂等；循环由队列驱动，按 waiting > 0 扩。我最早设计过带 CPU 和 slot 占比的多信号版本，加压测试发现 CPU 既有假阳性也有假阴性，slot 信号在 FE 准入机制下根本到不了，于是整个删掉。容量是离散的，不按单条查询算：节点启动约 66 秒，backend 注册约 2 分钟，而重查询跑 60 到 500 秒，按单条查询弹性多半会来晚。就绪判断分层，并假设每个信号都会说谎：不信 pod 数，要求 SHOW BACKENDS 里目标组存活，再要求一条 canary 查询真正读到存储（SELECT 1 会被 FE 常量折叠，根本不会发到 backend）。

缓存预热，说准确。 file cache 放在持久卷上，所以 backend 重启后是重新加载缓存，不是从空开始。预热以 Doris 的 warm-up job 形式跑，放在单独的 workload group 里，这也让它们不进第 5 节的成本核算。没做到的：激活一个新成员时不会等预热跑完，所以新成员会带着冷缓存服务一段时间。

证据。 heavy 召回 15/15（canonical 套件，生产规模 preprod）。light 精度 45/50 = 90%，样本是从生产 query log 里抽的 50 条真实查询，但跑在缩小 500 倍的表上，是早期分类器版本。在线 FE 上，14 个声明形状全部一致。那 197 条 Java/Python 语料是两套实现之间的一致性检查，不是准确率。总成本：降低约 29%。这是估算值，没有和账单对过账。深度文章：w-p-routing（引擎级路由）、w-p-elastic（弹性计算层）、w-p-fanout（点查扇出，第三项引擎改动）。

3. 生产数据迁移

问题。 事件表约 3,700 列宽，每个 region 有数十亿行。迁它会撞到窄表上不会出现的极限。

我做了什么。 我设计了面向生产 region 的 ClickHouse 到 Doris 迁移方案：总量约 1,000 亿行、最宽约 4,000 列。管线是从 ClickHouse 快照导出到 S3，再导入 Doris 原生表。四个内存断点要分别处理：Parquet footer（row group 数乘列数，单文件 2.12 GB）、exec_mem_limit 管不到的 scanner 内存（每个 backend 约 78 GB）、导出缓冲的取舍、以及随目标表增长的导入内存。约 17 亿行处导入出现 livelock：40 GiB 基线再加每次导入 25 GiB，两个并发导入就冲破 90 GiB 上限，并发钳到 1 解决。compaction 出过两次事故，我始终分开讲：建表时关了 auto-compaction（compaction score 约 2,500，每个 tablet 约 2,500 个 segment），以及被 DROP 的表留下的孤儿 tablet（score 约 4,504）。第一次的修复（auto-compaction 常开、2 GiB 写缓冲、按月动态分桶）把一个 tablet 从约 2,500 个 segment 降到约 10 个。

证据。 验证是在 preprod 里用最大事件表的生产规模副本做的，行数对账 99.945%。差的 0.055% 归因于源端重复行在去重语义下被合并；这个归因是按机制判断的，我没有保留逐行表。compaction 修复只在约 6% 的数据切片上验证过，不是全表。深度文章：w-cs-doris。

4. 容量与灾备

问题。 早先的容量规划按 15 TB 算，那是一块 EBS 卷的大小，不是数据量。另外，还没有人真跑过一次恢复。

我做了什么：容量。 我用实测的源端体量重做了规划：三张宽表，6.4 TiB。把卷大小换成数据量，去掉了约 2.5 倍的多配。池深度取自 90 天的小时峰值并发，先剔除 35 个被积压撑高的小时：p50 9、p90 23、p99 60.8、max 138。我用 p99 作为常驻水位的锚点，尾部留给弹性容量。这个模型只覆盖一个生产 region，其中几项输入标着「推断」。

我做了什么：灾备。 存算分离里要保护的是元数据，数据在 S3 上。我做了一套工具链：每 12 小时把元数据 bundle 到 S3；5 阶段原地恢复，所有破坏性操作隔离在一个 CLI 里；通过 API 做跨集群拷贝；以及 precheck、teardown、guard 命令。我评估过元数据 KV 的时间点恢复层，9 月下旬放弃了。S3 版本控制目前是关的。

证据。 全部是上线前测的。preprod 里原地恢复 2.74 TB / 1,799 个 tablet：clear 到 promote 55 分钟，其中约 25 分钟花在一次失败和重试上。dev 集群上完整端到端 DR：约 22 分钟。故障注入 17 个场景（dev 集群），15 个验证零丢数。演练最有价值的产出是 runbook 里的 8 处缺口和 1 个工具 bug。我不发布 RTO：一次非生产、单一规模的演练撑不起承诺。深度文章：w-p-doris-dr。

5. 基于审计日志的租户级成本归因

问题。 客户付的是固定套餐费，所以没人能说清哪个租户用了多少，也说不清平台成本里有多少是闲置容量。

我做了什么。 我在 Doris 内部用 SQL 加定时 Doris JOB 实现，读 __internal_schema.audit_log。每 5 分钟对存活 backend 做一次快照，得到每个计算组的小时单价。一条查询的成本是它的 slot 时长乘以它所在 workload group 的 slot 单价；S3 读按它从远端存储拉取的字节计；S3 存储按租户库每天计。预热、compaction、缓存命中和失败的查询不计费（失败的记为损耗）。闲置容量就是剩下的：计算组成本减去计费部分、减去运维账号、减去失败损耗。因为 audit log 只保留 30 天，每小时的摄取任务会把它拷进事实表。

证据。 preprod，35 天，422,150 条查询。查询成本之和与租户汇总、与计算组对账，差额为 0。正常查询里约 81% 不到 $0.00001。preprod 每天约 $40，按查询计量的计算加 S3 读约占 0.1%，S3 存储 18%，其余是闲置容量和平台固定成本；计算组利用率 0.5%。这些流量主要是压测和运维账号，所以我只拿它检验算法，不当作生产租户的结论。没做的：按租户配额分摊 FE 等公共组件（preprod 没有 per-tenant 配额）。

6. 可观测性

问题。 平台起步时没有大盘也没有告警，而它大部分故障是静默的。早期三次事故定了目标：预热任务指向一个已被删除的计算组，失败了 35 小时；平台 CI 覆盖了计算平台的状态，反复 5 次才有人把它们连起来；元数据存储唯一的健康信号冻结了 16 天，面板上一直是绿的。

我做了什么。 一套13 个分区、95 个面板的大盘，按两级分诊组织。第一级是给刚被叫醒、没有任何上下文的人一分钟看完的，按层排列，第一屏就能说出是哪一层出问题。第二级沿同样的层拆分，从第一级下钻落到的是一个有名字的分区，而不是在几十张图里翻。autoscaler 单独一个视图，因为它坏的时候，其他面板可以全绿，而容量已经不再跟随需求。告警我先写了 27 条候选，每条表达式都用真实指标验证，最后留下 12 条。筛选只有一句话：只留能抓住静默失效或不可逆故障的规则。每条容易自身失明的规则，都配了一条盯着指标是否消失的规则，因为针对一个已经消失的序列的告警永远不会触发。

证据。 表达式用真实数据验证过；触发行为没有端到端验证（没做变异测试）。它们是针对静默失效的 SLI/SLO 式健康信号，不是延迟 burn-rate 告警，延迟 SLO 层还没建。深度文章：w-p-doris-obs。
