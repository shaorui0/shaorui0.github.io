0. Context and architecture

This is a Claude Code skill plus a set of shell hooks. An alert goes in; a report with an evidence chain and a drafted command list comes out; a human runs any command that touches production. The animated model above shows the flow, so I will not redraw it. The one idea to hold on to is the split of labor: the main agent only judges and writes commands, subagents do all the raw fetching of metrics, logs and Slack, and every irreversible step sits behind code that returns an exit code. The public repo is shaorui0/agents. The knowledge base behind it is 108 files (measured). The animated replay on the home page is a representative trace I composed to show the flow, not a recording of one real incident.

1. Context budget: fetching is pushed to subagents

Problem. The scarce thing in an investigation is the main agent's context, not the model. One raw range query can come back at around 30K tokens, and a slice of logs is worse. If the main agent pulls that itself, it reaches the phase where the hard calls are made with its window already full of numbers.

What I did. The main agent keeps three things: navigation, judgment, command generation. Every metric, log and Slack read goes to a subagent that returns a structured summary of at most 500 tokens: the max with its timestamp, a step-jump flag, and a ratio against baseline. Query safety rules (label filter, step floor, time ceiling) live in their own skill so each subagent inherits them.

Evidence. The 30K figure is what I saw from raw queries while building this; I did not run a controlled benchmark of main-agent versus subagent fetching. The 500-token limit is a prompt contract, so it is advised, not enforced; nothing in code rejects a longer summary.

2. Phased tool unlock: A investigate, B decide, C operate

Problem. A familiar failure: the agent sees a deploy record and invents a root cause before the symptom is understood. "What changed recently" is a strong attractor.

What I did. A phase: field at the top of the per-investigation plan.md limits what the main agent may read. In phase A it can read debug trees, patterns and read-only metrics, but not deploy history, so it has nothing to confabulate from. A to B requires a non-empty hypothesis list with at least one verified. B unlocks full cases and deploy history; B to C requires the user to confirm the root cause explicitly. Only in C can it read runbook bodies and draft commands. Each transition is logged in plan.md with a time and a reason.

Evidence. This is a design with a written precondition, enforced by path rules in the skill text. It is advised, not code. I have no measured before/after on how often the anchoring failure happens, so I do not claim one.

3. Deterministic gates: the model judges, code owns irreversible actions

Problem. Models hallucinate, so safety cannot depend on the model complying.

What I did. A mutating command must pass four gates. Gate 1 is explicit user approval; without it the command stays in the report. Gate 2 is the static allow/deny table in settings.json. Gate 3 is k8s_gate, a PreToolUse hook: it maps a cluster alias to a tier, checks a hard-block table (namespace and volume deletes, all-namespace deletes, IAM changes, instance terminate), detects mutating verbs by position, splits compound commands and takes the strictest segment. Production plus mutating exits 2 and prints the command for a human. An alias that is not in the map is treated as production, so the gate fails closed. Gate 4 is mandatory post-change verification. The agent writes a # INTENT: line before each mutating command, and a pre/post audit pair records it.

Evidence. 48 tests pass locally (30 gate, 7 audit, 11 report verifier), run on synthetic commands with no cluster or credentials. These tests prove the gate's logic, not that production was ever protected by it. Known limits I wrote down: a verb deny-list is open for verbs it has never seen, and a script file or shell function that calls kubectl is invisible to Gate 3; Gate 2 and the audit log are the second line. Gates 1 and 4 are advised in the skill; Gates 2 and 3 are enforced.

4. Knowledge compounding and a report that can fail

Problem. A saved report is not learning, and a report that reads well is not a correct one.

What I did. After an investigation the agent judges the delta against existing files: a match updates that file, a new root-cause path creates a case, a new signal updates the routing table. AI-written entries stay draft until I promote them, and each carries derived_from pointing at its report. Separately, verify.py turns "good report" into an exit code: required sections present, every conclusion cites an evidence id, over-assertion words such as "definitely" rejected, and an INTENT on each mutating command. It reuses the gate's own classifier so the two cannot drift.

Evidence. The knowledge base is 108 files, counted on disk. The verifier is tested on a passing and a failing fixture (exit 0 and exit 2). I do not have a measured trend of report quality over time; the aggregate tracking is not something I can show numbers for.

5. What an investigation looks like: latency spike, backend or network

The latency-spike workflow shows the style. First check the alert is still firing; if it never fired, run the false-alarm tree and stop. Then three subagents fetch in parallel over a window of plus or minus 3 minutes around the event: total request time, upstream response time, upstream connect time. The decision is arithmetic: total is roughly front gap plus connect plus upstream response. On one production tenant I looked at, connect stayed near 1 ms, the front gap near 0, and total over upstream response was 1.00, so the time was all in the backend and not in the network path. A missing client, cluster or event time stops the run and asks the user instead of guessing. This is a single tenant on one occasion, an example of the method, not a statistic. It also has a known blind spot: the exporter's quantile 1.0 smooths a single 5-second spike to about 0.3 s, so a P100 question goes to raw logs.

Boundaries

  • The agent cannot change production. Mutating commands are blocked by the gate hook, and its token has no write permission on production clusters; commands go to a human.
  • I do not publish alert volume or time-saved figures for this agent; there is no original record behind such numbers.
  • The full incident write-ups and investigation records are not public; the repo holds sanitized material and a leak scan that returns zero hits (which proves absence of known patterns only).
  • Phase lock, the 500-token contract and Gates 1 and 4 are prompt-level rules. Only Gate 2, Gate 3 and the verifier return exit codes.

0. 背景与架构

这是一个 Claude Code skill 加一组 shell hook。告警进去，出来的是一份带证据链的报告和一份草拟的命令清单；凡是碰线上的命令，由人来执行。上面的动画已经演示了流程，这里不重画。要记住的只有分工：主 agent 只做判断和写命令，指标、日志、Slack 的原始数据全部由 subagent 去取，每一步不可逆操作都放在会返回 exit code 的代码后面。公开仓库是 shaorui0/agents，背后的知识库是 108 个文件（实测）。首页的动画回放是我编的一条「代表性轨迹」，用来展示流程，不是某一次真实故障的录像。

1. Context 预算：取数下沉给 subagent

问题。 调查里稀缺的是主 agent 的 context，不是模型。一次 raw range query 可能回来约 3 万 token，一段日志更多。主 agent 自己去拉的话，走到该下关键判断的阶段，窗口已经被数字塞满。

我做了什么。 主 agent 只留三件事：导航、判断、生成命令。所有指标、日志、Slack 读取都交给 subagent，只回收不超过 500 token 的结构化摘要：最大值和时间戳、有没有阶跃、相对基线的倍数。查询安全规则（label 过滤、step 下限、时间上限）单独放在一个 skill 里，每个 subagent 都继承。

证据。 3 万这个数是我搭系统时看到的 raw query 返回量；我没有做过「主 agent 自己取 vs subagent 取」的对照实验。500 token 的上限是 prompt 约定，属于建议而非强制，代码里没有任何东西会拒绝更长的摘要。

2. 分阶段解锁工具：A 调查、B 决策、C 操作

问题。 一个常见的失败：agent 看到一条部署记录，症状还没搞清楚就编出一个根因。「最近改了什么」的吸引力很强。

我做了什么。 每次调查的 plan.md 顶部有个 phase: 字段，限制主 agent 能读什么。phase A 能读 debug tree、pattern 和只读指标，但读不到部署历史，所以没有东西可以拿来编。A 到 B 要求假设列表非空且至少一条被验证。B 解锁完整 case 和部署历史；B 到 C 要求用户明确确认根因。只有 C 才能读 runbook 正文、起草命令。每次切换都在 plan.md 里记时间和原因。

证据。 这是有书面前置条件的设计，靠 skill 里的路径规则执行，属于建议，不是代码强制。我没有「前后对比锚定失败发生率」的实测，所以不声称有效果数字。

3. 确定性门禁：模型负责判断，不可逆动作归代码

问题。 模型会幻觉，所以安全不能靠模型听话。

我做了什么。 一条会改东西的命令要过四道门。门 1 是用户明确批准，没批准命令就留在报告里。门 2 是 settings.json 里的静态 allow/deny 表。门 3 是 k8s_gate，一个 PreToolUse hook：把集群别名映射到环境等级，检查硬拦截表（删 namespace 和卷、全 namespace 删除、IAM 变更、终止实例），按位置识别变更动词，拆开复合命令并取最严的一段。生产加变更直接 exit 2，并把命令打印出来给人去跑。不在映射表里的别名一律当生产，所以是 fail-closed。门 4 是变更后强制验证。agent 每条变更命令前要写 # INTENT: 一行，前后各一条审计记录。

证据。 本地 48 个测试通过（门 30、审计 7、报告校验 11），用的是合成命令，不需要集群和凭证。这些测试证明的是门的逻辑，不证明线上真的被它保护过。我写明的已知局限：动词黑名单对没见过的动词是放行的；通过脚本文件或 shell 函数调用 kubectl，门 3 看不见，靠门 2 和审计日志兜底。门 1 和门 4 在 skill 里是建议；门 2 和门 3 是强制。

4. 知识沉淀，以及一份会判不及格的报告

问题。 存一份报告不等于学到东西；一份读起来顺的报告也不等于对。

我做了什么。 调查结束后，agent 对照已有文件判断增量：命中就更新那个文件，新根因路径就建一个 case，新信号就更新路由表。AI 写的条目保持 draft，由我晋升，每条带 derived_from 指回它的报告。另外 verify.py 把「报告好不好」变成一个 exit code：必需章节齐全、每个结论引用证据编号、拒绝「definitely」这类过度断言的词、每条变更命令都有 INTENT。它复用门自己的分类器，两边不会漂移。

证据。 知识库 108 个文件，按磁盘实数。校验器用一个通过、一个失败的 fixture 测过（exit 0 和 exit 2）。报告质量随时间的趋势我没有实测数据，这部分的汇总追踪拿不出数字。

5. 一次调查长什么样：延迟尖刺，后端还是网络

延迟尖刺的流程能看出风格。先确认告警还在 firing；从没触发过就走假警报判定树并停止。然后三个 subagent 并行取数，窗口是事件时间前后各 3 分钟：总请求时间、upstream 响应时间、upstream 建连时间。判定是算术：总时间约等于前段间隙加建连加 upstream 响应。我看过的一个生产租户上，建连稳定在约 1 ms，前段间隙接近 0，总时间除以 upstream 响应是 1.00，所以时间全在后端，不在网络链路。缺 client、cluster 或事件时间就停下来问用户，不猜。这是单个租户、单次的观察，用来说明方法，不是统计结论。它还有个已知盲区：exporter 的 quantile 1.0 会把一次 5 秒的尖刺抹成约 0.3 秒，所以问 P100 要去查原始日志。

边界

  • agent 改不了生产：变更命令被 hook 拦住，它用的 token 在生产集群上也没有写权限，命令交给人去跑。
  • 我不公布这个 agent 的告警量或节省时间的数字，因为背后没有原始记录。
  • 完整的故障复盘和调查记录不公开；仓库里是脱敏材料，加一个扫描结果为零命中的泄漏检查（它只能证明已知模式不存在）。
  • phase lock、500 token 约定、门 1 和门 4 是 prompt 层规则。只有门 2、门 3 和校验器会返回 exit code。
