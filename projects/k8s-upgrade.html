0. Context and architecture

The fleet was 50 self-managed clusters on AWS: kubeadm control planes and ASG-backed workers. 1.24 was going out of support, and kubeadm moves one minor at a time, so every cluster needed several hops, each touching control plane, workers and addons. Done by hand, one cluster took 18-21 hours and two people, because the judgment about "is it safe to go on" lived in senior heads. I built a CLI (Python, driving Ansible, boto3 and kubectl) that turns that judgment into written gates with recorded evidence, and ran the fleet through it.

The animated model above shows the flow, so I will not redraw it. In words: check, plan as a real dry-run, a human gate, apply (masters one at a time, each held until the apiserver answers /readyz), workers in 20% batches, addons, verify against the pre-upgrade baseline. Fleet order is dev, preprod, prod canary, the rest of prod, management cluster last. Any failure pauses the whole fleet until a person restarts it.

A public repository, k8s_upgrade_safety, holds a clean-room model of this approach: the same gates as a state machine, run by a simulator against a synthetic fleet with planted faults. It is not the production code and contains none of its names, schemas or data. Where this page cites test counts, they come from that model.

1. Making "safe to proceed" something that can fail

Problem. Nobody could answer, at a given step, what evidence said the next step was safe. Postmortems were reconstructions from memory. A written plan cannot fail, so it catches nothing.

What I did. Every gate is a written criterion with a fixed threshold, evaluated by code, leaving a JSON record. Examples: etcd member list, raft index lag (a follower more than 1,000 entries behind fails the check, since quorum can exist on paper while replication is unhealthy), leader uniqueness, and a mandatory etcd snapshot before anything mutates. The plan stage actually diffs: kubeadm upgrade plan and ansible --check --diff for masters, AMI and Launch Template diffs for workers (only the AMI ID may change). Blast radius is arithmetic done up front: three masters tolerate one down, serial: 1 touches one. After the run, verify compares against the baseline file recorded before it started, not against anyone's recollection.

Evidence. The model repo runs 149 tests, and a mutation check that breaks the gates on purpose (raft limit raised to 3,000, /readyz probe always true, PDB not treated as a blocker, completed steps re-run on resume and so on) reports 25 of 25 mutations caught. That shows the gate logic is internally consistent and its evidence is reproducible, on a simulator. It says nothing about real kubeadm, etcd or AWS behavior.

2. Two preprod incidents and the guardrails they left

Problem. Both happened in preprod, during the validation stage, and neither reached a production cluster. They matter because each one broke an assumption the design rested on.

The etcd data path. A year earlier, an on-call engineer had moved etcd's data directory to a new volume on two of three masters during a disk-pressure alert, and never wrote it back into the playbook or the kubeadm config. kubeadm upgrade re-renders the etcd manifest from config, which pointed back at the canonical path. When the first drifted master was upgraded, etcd lost its data; when the second followed, quorum was gone and all three apiservers failed. serial: 1 bounds the order of operations, not the correlation of inputs: two masters carrying the same drift will fail one after the other. The fix was to bring the paths and volume sizes under version control and add a consistency check across all masters, run before touching the first one. That check became a required step in the production upgrade process.

Worker refresh. Instance Refresh judges a new node healthy from EC2 and target-group checks, neither of which knows about Kubernetes. A kubeadm join in the bootstrap script had been wrapped in || true long before, to ride out a transient DNS failure. When a refresh outlived the cached join token, joins started failing every time, the error was swallowed, and the batches kept going green. Old capacity was replaced by nodes that never became Ready. The fix had three parts: a fresh join token per refresh, no error swallowing in bootstrap, and a gate between batches that checks the node is Ready in Kubernetes. All three went into the production worker process.

Evidence. Both are accounts from my own work in preprod; there is no ticket or commit I can point to, and I do not cite one. The effect I can state: after these checks were in the process, the production clusters did not repeat either failure.

3. Order and per-layer gates in apply

Problem. A fleet upgrade fails in the gaps between layers: a control plane that is up but not yet serving, workers that join before the cloud controller is healthy, a drain that a PDB quietly blocks.

What I did. Masters go one at a time, and the next component on a master does not move until the apiserver passes /readyz and is a healthy load-balancer member. Workers are replaced immutably in 20% batches that pause on failure. Addons go in dependency order: the AWS cloud-controller-manager first (an unhealthy one leaves new workers stuck on the uninitialized taint), then the CNI, then Cluster Autoscaler, each with its own check. Rollback triggers are written before execution, per layer: snapshot restore plus binary downgrade for the control plane, stop the refresh and revert the Launch Template for workers, rollout undo for addons. Drift between clusters is handled by cluster_type plus a few per-cluster flags (for example a drain timeout of 600 s instead of 300 s where eviction is slow), and it shows up in the check baseline.

Evidence. In the model, each of four planted faults stops the run at the step the method names: raft lag over the limit stops at check, a failing /readyz stops before controller-manager, a PDB that blocks the canary drain stops with nothing forced, a CCM broken by the new control plane stops the worker layer before any worker. Production: all 50 clusters on 1.29, zero customer-impacting incidents and no rollbacks.

4. Time per cluster, and what "zero incidents" rests on

Problem. The manual figure was 18-21 hours with two people, which is 36-42 person-hours per cluster, multiplied by 50 clusters and several hops.

What I did. One operator plus the system, with human sign-off at check, plan, each master and final verify. Interrupted runs resume from a per-step state file and do not repeat completed steps.

Evidence. 6-8 hours per cluster, one operator. That is roughly five times fewer person-hours, and a smaller drop in wall-clock time. These are the figures from running the production fleets, not from a controlled benchmark. For the zero-incident result, the largest single factor was architectural: the production fleets are paired, so I moved traffic to the sibling cluster, paused cross-cluster replication, upgraded the dark cluster, waited for replication lag to drain, verified, and moved traffic back. Care in the process helped, but a dark cluster is what turned most mistakes into non-events. I say this up front because the claim would otherwise credit the process with more than it earned.

Boundaries

  • A target of 3-4 hours per cluster exists, depending on three automations (external alert gating, synthetic health checks, auto-promotion after canary). None is built. The achieved figure is 6-8 hours.
  • The two preprod incidents did not happen in production. The guardrails they produced are in the production process.
  • The public repository is a model run on a simulator. It is not the production code, and it proves nothing about real kubeadm, etcd or AWS.
  • I do not publish per-cluster timings, cluster names or incident tickets.

0. 背景与架构

集群规模是 AWS 上 50 个自管集群：kubeadm 控制面，ASG 托管的 worker。1.24 即将脱离支持，而 kubeadm 一次只能升一个 minor，所以每个集群要走好几跳，每一跳都覆盖控制面、worker 和 addon 三层。纯手工的话，一个集群要 18-21 小时、两个人，因为「能不能继续」这个判断只存在于资深工程师的脑子里。我做了一个 CLI（Python，调用 Ansible、boto3 和 kubectl），把这个判断变成写下来的门禁和留档的证据，然后让整个集群群走这条流程。

上面的动画模型已经展示了流程，这里不再重画。用文字说：check，作为真实 dry-run 的 plan，一道人工闸门，apply（master 逐台推进，每台等 apiserver 的 /readyz 通过才放行），worker 按 20% 批次，addon，最后和升级前的 baseline 对照 verify。集群推进顺序是 dev、preprod、prod 金丝雀、其余 prod，管理集群最后。任何一次失败，整个集群群暂停，由人重启。

公开仓库 k8s_upgrade_safety 里是这套方法的 clean-room 模型：同样的门禁写成状态机，由模拟器在带有预置故障的合成集群上运行。它不是生产代码，不含生产的名字、schema 或数据。本页引用的测试数字都来自这个模型。

1. 让「可以继续」成为一个会失败的判断

问题。 在任何一步，没人能说出凭什么证据确认下一步是安全的。复盘只能靠回忆。写在文档里的计划不会失败，所以什么也拦不住。

我做了什么。 每道门都是一条写明的标准，带固定阈值，由代码判定，并留下 JSON 记录。例如：etcd member list、raft index lag（follower 落后 leader 超过 1,000 条就判失败，因为 quorum 在名义上存在时，复制也可能是不健康的）、leader 唯一性，以及任何变更之前强制做一次 etcd snapshot。plan 阶段真的会比对：master 侧是 kubeadm upgrade plan 加 ansible --check --diff，worker 侧是 AMI 和 Launch Template 的 diff（只允许 AMI ID 变化）。blast radius 在执行前用算术定下来：三台 master 容忍一台不可用，serial: 1 一次只动一台。运行结束后，verify 对照的是升级开始前落盘的 baseline，不是谁的记忆。

证据。 模型仓库跑 149 个测试，另有一个变异检查，故意把门禁弄坏（raft 上限放宽到 3,000、/readyz 探测恒为真、PDB 不再算阻塞、恢复时重跑已完成步骤等等），25 个变异全部被抓到。这能说明门禁逻辑自洽、证据可复现，但是在模拟器上。它不能说明真实的 kubeadm、etcd 或 AWS 的行为。

2. 两次 preprod 事故和它们留下的护栏

问题。 两次都发生在 preprod 的验证阶段，都没有流入任何生产集群。它们重要，是因为每一次都打穿了设计所依赖的一条假设。

etcd 数据路径。 一年前一次磁盘压力告警，on-call 的同事在三台 master 里的两台上把 etcd 数据目录挪到了新卷，没有回填到 playbook 和 kubeadm 配置里。kubeadm upgrade 会按配置重新渲染 etcd 的 manifest，指回规范路径。升级第一台漂移的 master 时，etcd 丢了自己的数据；第二台跟着升级后，quorum 没了，三个 apiserver 全部失败。serial: 1 限制的是操作顺序，不限制输入的相关性：两台带着同样漂移的 master，早晚会一台接一台出问题。修复是把路径和卷大小收进版本控制，并加一条跨所有 master 的一致性校验，在碰第一台之前就跑完。这条校验成了生产升级流程里的必过项。

worker 刷新。 Instance Refresh 判断新节点是否健康，看的是 EC2 和 target group 的检查，这两层都不知道 Kubernetes 的存在。bootstrap 脚本里的 kubeadm join 很早以前被包了一层 || true，为了扛过偶发的 DNS 失败。一次刷新跑得比缓存的 join token 有效期还久，之后每次 join 都失败，错误被吞掉，批次一直绿灯。旧容量被一批从未 Ready 的节点换掉了。修复有三部分：每次刷新前现生成 join token，bootstrap 里不再吞错误，批次之间加一道门，检查节点在 Kubernetes 里是 Ready。三条都进了生产的 worker 流程。

证据。 两件事都是我自己在 preprod 处理的，没有工单或 commit 可以指，我也不引用。我能说的结果是：这些检查进了流程之后，生产集群没有重复这两种故障。

3. apply 里的顺序和逐层门禁

问题。 集群群升级是在层与层的缝隙里出事的：控制面起来了但还没法服务，cloud controller 还不健康 worker 就加入了，PDB 悄悄卡住 drain。

我做了什么。 master 一次一台，同一台上的下一个组件要等 apiserver 通过 /readyz 并成为健康的负载均衡成员才会动。worker 做不可变替换，20% 一批，失败即暂停。addon 按依赖顺序：先是 AWS cloud-controller-manager（它不健康时，新 worker 会卡在 uninitialized taint 上），然后 CNI，然后 Cluster Autoscaler，每一个都有自己的检查。回滚触发条件在执行前按层写好：控制面是 snapshot 恢复加二进制降级，worker 是停止刷新并回退 Launch Template，addon 是 rollout undo。集群之间的漂移用 cluster_type 加少量 per-cluster flag 处理（比如驱逐慢的集群把 drain 超时从 300 秒调到 600 秒），并且会体现在 check 的 baseline 里。

证据。 在模型里，四个预置故障各自停在方法规定的那一步：raft lag 超限停在 check，/readyz 失败停在 controller-manager 之前，PDB 卡住金丝雀 drain 时停下、不强制驱逐，被新控制面弄坏的 CCM 让 worker 层在任何 worker 之前就停下。生产：50 个集群全部升到 1.29，没有客户可感知的事故，没有回滚。

4. 单集群耗时，以及「零事故」靠什么

问题。 手工是 18-21 小时、两个人，也就是每个集群 36-42 人时，再乘以 50 个集群和多跳。

我做了什么。 一个操作人加这套系统，人工签核保留在 check、plan、每台 master 和最后的 verify。中断的运行可以从逐步状态文件恢复，不重复已完成的步骤。

证据。 单集群 6-8 小时，一个操作人。人时大约降了五倍，墙钟时间的降幅小一些。这些是生产集群实际跑出来的数字，不是对照实验。至于零事故，最大的单一因素是架构上的：生产集群是成对部署的，所以我先把流量切到对侧集群，暂停跨集群复制，升级已经没有流量的这一侧，等复制 lag 回落，验证，再把流量切回来。流程上的谨慎有帮助，但让大多数失误变成无事发生的，是这个无流量的集群。我先说这一点，是因为不说的话，这个结论会把功劳多算给流程。

边界

  • 单集群 3-4 小时只是目标，依赖三项自动化（外部告警门控、synthetic health check、金丝雀通过后自动放行），一项都没做。已达成的是 6-8 小时。
  • 两次 preprod 事故没有发生在生产。它们产生的护栏在生产流程里。
  • 公开仓库是在模拟器上跑的模型，不是生产代码，也不能证明真实 kubeadm、etcd 或 AWS 的行为。
  • 我不公开单集群的具体耗时、集群名或事故工单。
